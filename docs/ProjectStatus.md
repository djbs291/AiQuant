# AiQuant — Project Status & Roadmap

*Snapshot taken 2026-09-13 at `main` = `fa04ec0` (last commit 2025-11-09). Last updated 2026-09-23, after PR #24 (`41a24e9`); §2–§4 still describe the original snapshot, while §5 and §6 are kept current.*

## 1. What the project is

AiQuant is a C++20 engine for algorithmic-trading research. It ingests tick data from CSV, resamples it into OHLCV candles, and computes technical indicators. It then trains a ridge linear model to predict the next candle's close-to-close delta, and backtests a rule-based signal engine that also uses the model's prediction. Everything can be driven by an INI "scenario" through a CLI, a small HTTP service, or a Python module.

The target architecture is described in `docs/CppFinancialAIEngine.md`, with per-layer designs in `docs/CoreLayerDesign_*`, `docs/IndicatorsLayerDesign_*` and `docs/IOLayerDesign_*`. The MVP described there is implemented. The real-time, performance and integration parts of that design are not implemented yet.

10. ~~`IModel::fit` / `partial_fit` default to throwing `logic_error`. Training happens only through the free function `train_linear_from_feature_rows`, and there is no online learning.~~ Fixed 2026-09-17: `fin::ml::SgdRegressor` implements both, `model = sgd` selects it, and `online_update = true` keeps it training through the out-of-sample stretch — one `partial_fit` per candle that closes, always one row behind so the replay reads no candle before it has happened. The base-class defaults still throw for `LinearModel`, which is a closed-form fit with nothing to update. **Three caveats, all by design:** `model_out` writes the model *as trained*, before any online update, so the file is the artifact of the training run and not of the replay; the standardizer keeps Welford moments over every sample, so its estimates keep moving and the same feature vector can score differently after further updates; and the learning rate has to be tuned per feature set, since a rate that suits one scale of target deltas will crawl or diverge on another (the model reports divergence naming the rate instead of emitting NaNs).
11. ~~`FeatureBus`, and therefore the model and scenarios, uses only EMA/RSI/MACD. Bollinger Bands, ATR, ADX, Stochastic, VWAP, Z-Score and Momentum are implemented and tested but not available as model features.~~ Fixed 2026-09-17: the `features` key selects any of 20 names from `feature_catalog()`. **Two caveats:** the catalogue builds one indicator per output, so selecting `macd,macd_signal,macd_hist` runs three `MACD` objects over the same closes (identical results, more work — a provider layer would fix it if profiling ever justifies one); and `vwap` accumulates from the first candle with no session reset, so on a multi-day file it drifts toward a whole-file average.
12. ~~**RSI seeded one delta short.**~~ Fixed 2026-09-17, found by the TA-Lib golden tests. `RSI::update` accumulated `period - 1` deltas and divided by `period`, so the first value was both one bar early (bar 13 instead of 14 for a 14-period RSI) and wrong: 78.5758 where Wilder's definition, computed by hand and confirmed by `TA_RSI`, gives 78.5609. The error propagated through the smoothing (bar 18: 84.52 vs 84.20). The fix seeds on the first `period` deltas. Impact on the MVP scenario was small: same 300 candles, same warmup 33, same 267 feature rows, same 18 trades and PnL 0.6811; validation RMSE moved 0.00358 → 0.00357.
13. ~~**ADX truncated its DX seed.**~~ Fixed 2026-09-17, also found by the golden tests. `ADX.hpp` declared `std::size_t dx_sum_ = 0.0`, so every DX was truncated to an integer before being averaged into the first ADX. `-Wall -Wextra -Wpedantic` does not catch this; `-Wfloat-conversion` would. **Still open, by design:** even with the right type, our directional family does not match TA-Lib bar for bar during warmup. We seed ATR/±DM with the mean of the first `period` bars, as in Wilder's book; TA-Lib (`ta_ADX.c`) accumulates `period - 1` bars and then applies a smoothing step, so its first value carries one extra decay. Both readings are defensible, and the gap decays: 4e-3 at the first bar, 5e-4 by bar 100, 1e-6 by bar 200, 8e-10 by bar 300. The golden tests therefore compare ADX and ±DI from bar 250 onward.

14. ~~**The batch path blends multi-symbol tick files.** The symbol is parsed into `Tick` and then dropped: `TickToCandleResampler` has no symbol field, so `resample_csv_with_stats` — and therefore `run_scenario`, the HTTP scenario endpoints and the Python module — merges every symbol in a file into one candle series without a word.~~ Fixed 2026-09-21, and demonstrated first: on a file holding `ABC` around 100 and `XYZ` around 900, every bar came out `open=100+i, high=900+i, low=100+i, close=900+i` — one instrument's open against another's close. The filtering lives in the pipeline helpers rather than in the resampler, which stays per-symbol by construction and was not touched; `resample_csv_with_stats` takes an optional symbol, binds to the first tick's symbol when none is given, and counts the rest in `PipelineResult::ticks_other_symbol`. Scenarios reach it through a new `symbol` key, and the resolved symbol and skipped count are reported in the JSON. This mirrors the `SymbolPolicy` the streaming path has had since PR #21, so batch and stream now agree — which is what the anchor test in `tests/stream/test_stream_matches_batch.cpp` exists to protect. **Deliberately not done:** splitting a file into one series *per* symbol. That would change the shape of `PipelineResult` and every caller, need an ordering or hash on `fin::core::Symbol`, and invent multi-asset semantics that nothing downstream can consume — the `Backtester` is long-only and single-asset. Per-symbol streaming workers can now be built on the same shape.

15. ~~**The tick CSV reader accepted almost anything, including an out-of-bounds read.**~~ Fixed 2026-09-20, found by pointing the sanitizers at deliberately malformed files while sizing the Quality work. Five distinct defects, each now demonstrated by a regression test: (1) a header missing a required column left `find_idx` returning `-1` while the width guard compared only the *largest* index against the row, so `cols[-1]` read off the front of the vector — ASan reported a heap-buffer-overflow; (2) `std::from_chars` was checked for `ec` but never for full consumption, so `1.5abc` parsed as `1.5` and `123xyz` as `123`, unlike the INI and JSON parsers which had always required `ptr == end`; (3) `nan` and `inf` were accepted as prices, and a NaN is the worst case because the resampler's `>` and `<` comparisons are both false for it, so the bar's high and low silently keep the wrong values; (4) `ms * 1'000'000` in `from_epoch_ms` had no range check, and UBSan reported signed-integer-overflow for a timestamp past the year 2262; (5) negative prices and volumes were accepted. `ReadStats::rows` also counted the header, so `rows == parsed + skipped` never held; it now does, and a property test asserts it over randomized rows. A file-level problem — unopenable, or a missing column — is now reported through `FileTickSource::error()` and `PipelineResult::error`, so `run_scenario` names the column instead of complaining about warmup. **Still open:** nothing stops a non-finite price entering through a non-CSV `ITickSource`, since `Price` and `Volume` remain unvalidated value wrappers and `Candle` does not check `high >= low`.

16. ~~**The engine could emit JSON that is not JSON, and the config accepted values that cannot mean anything.**~~ Fixed 2026-09-21. A degenerate config — `bb_period = 0`, say — left `training_mse` and `validation_rmse` NaN, and the writer streamed them straight out as a bare `nan`. Readers then disagreed: `jq` accepts it, while Python's `json`, JavaScript's `JSON.parse` and **this project's own `fin::app::json` reader** all reject it, so the same document was valid or not depending on who read it. Both writers are fixed — `scenario_result_to_json` and the `/predict` and `/signal` bodies in `http_main.cpp` now go through `fin::app::json::write_number`, which emits `null` for anything JSON cannot spell — and a test feeds the writer's output back into the project's own reader, so the two halves of the contract are held together. Upstream of that, the INI loader now rejects an unknown key (it was silently ignored, so `rsi_peroid = 20` trained the default and said nothing), a period of zero, a non-positive `bb_k` and a negative `ridge`. A third lax parser was found and fixed while here: `LinearModel::load_from_file` used the same `from_chars` without a full-consumption check that issue 15 fixed in the tick reader, so `close,0.5abc` loaded as `0.5` and `close,nan` loaded a NaN weight that turned every prediction into NaN — a malformed weight is now a failed load, because these files are machine-written and a value that does not parse means corruption.

17. ~~**The config accepted numbers that break the run, and only the INI loader checked any of them.**~~ Fixed 2026-09-23, found by the INI property test on its first run. Three defects: (1) `from_chars` parses `nan` and `inf`, and every range check is a comparison that NaN passes by being false both ways, so `ridge = nan` or `bb_k = inf` loaded; `train_ratio = nan` went on to `clamp_training_rows`, whose clamp NaN also slips through, and UBSan reported `nan is outside the range of representable values of type 'unsigned long'` at the cast. (2) Account values were never checked: on the MVP scenario `qty = -5` reported **+844% with zero trades**, because a Buy of a negative quantity pays out, `fee = -1000` turned all 18 trades into wins, `cash = nan` produced `null` metrics, and `rsi_buy`/`rsi_sell` accepted values outside `[0, 100]`. (3) The range checks lived only at the end of `load_scenario_file`, so the CLI flags, the Python dict and the HTTP JSON — which all build a `ScenarioConfig` directly — bypassed them: `run-mvp --ridge -1` trained exactly what the INI refused. The rules now live in `fin::app::validate_scenario_config`, which both the loader and `run_scenario` call; non-finite numbers are refused at the line that holds them; `cash`, `qty` must be positive, `fee` non-negative, RSI thresholds in `[0, 100]`, the `sgd_*` options are checked whatever the model, and the loader refuses `online_update` without `model = sgd` instead of leaving that to the run. `test_json_contract.cpp` had been reaching a NaN in the writer through `bb_period = 0` on a directly built config — the very gap closed here — so it now poisons a real result instead. **Two loose ends, closed 2026-09-23 in a follow-up:** a repeated key silently overrode the earlier one (`rsi = 10` then `rsi = 20`, or `sma` and its alias `sma_period`), and a `#` anywhere in a value started a comment, so `ticks = runs#3.csv` loaded `runs` and `rsi = 10#x` loaded 10. The loader now maps every alias to one canonical key before dispatching, so a field set twice under any spelling is refused with both line numbers, and a `#` starts an inline comment only after whitespace.

The anchor test replays the same CSV through both paths and requires the streaming path to produce the same candles, the same predictions and the same final `Metrics` as `run_scenario`. ✅ Per-symbol routing: `SymbolPolicy::Route` (`aiquant stream --per-symbol`) gives each symbol its own `SymbolPipeline` the first time it appears, instead of refusing or skipping it.
